# 组合故障与规模压力验收

日期：2026-11-06。代码位于共享目录 `D:\VMshare\clocktree7`，VM 从 `/mnt/hgfs/VMshare/clocktree7` 执行。此次从上一轮高扇出和端口超时问题继续检查通信开销、连续超时、内存轮换、崩溃提交边界、磁盘写入失败、缓存换出及深层展开。

## 发现与修改

| 发现 | 修改 | 验证方式 |
| --- | --- | --- |
| 每端口在共享目录写状态、轮询确认，短追踪的通信开销明显 | Linux 默认使用 `127.0.0.1` 本机连接传递临时开始/完成消息；控制进程收到消息即唤醒，不等待固定轮询周期；关闭 Nagle；阶段镜像检查间隔 0.1 秒 | 同一扇出 fixture 超时开关对照，8,194 路目标负载 |
| 通信异常不能重置当前端口计时，也不能让 worker 等待一个永远不会到来的确认 | 检查身份令牌、消息结构、trace 序号、实例/端口/方向；拒绝错序和已完成请求重放；活跃端口断连时报错保留断点 | 本机 socket 单元测试、真实 worker 被杀、确认前后控制进程被杀 |
| 超时决定写盘失败时，不应先改变内存中的跳过状态 | 新决定原子写盘成功后才更新内存状态；写入失败终止当前尝试，旧决定和已提交前缀保留 | 单元注入 ENOSPC；真实 Verdi 运行中注入决定写入失败，然后重新启动恢复 |
| 完整原始证据恢复不再启动 Verdi，但仍创建了临时监听，报告也缺通信方式 | 返回前明确关闭监听，并补齐报告字段 | 完成断点后杀控制进程、重开后仅重建结果，attempts 保持 1 |
| 当前 Verdi 2018 对 256 层 RTL 仅发出“超过 50 层、跳过展开”警告；生成 KDB 时也可能已经截断 | 导入阶段检测该警告并报错；KDB 有标准旁置 `elabcomLog/compiler.log` 时一并检查 | 真实 RTL 导入、真实 `vcs -kdb=only` 生成 KDB 后导入，两项均在枚举前停止 |
| 接近上述边界时可能没有编译警告，但 NPI 返回存在的 module 层次句柄，其定义名为空 | 查找前拒绝缺少已展开 module 定义的范围，日志提示核对展开限制/未解析 module | 48 层嵌套负例；40 层完整连接正例 |

持久断点、原始证据、超时决定仍写盘。临时本机通信没有替代恢复数据；每个端口正常返回后仍必须得到控制进程确认才可提交。默认 `port_trace_timeout_s: 0` 不开启此通信流程，任务总时长仍不限。只跳过超时的当前例化剩余端口，同名其他实例继续。

本机监听创建失败时自动回退文件确认，原因记入 `memory.json.trace_monitor_fallback`；也可显式设置 `CLOCKTREE_TRACE_TRANSPORT=file`。后者已做真实 Verdi 回归，自动创建失败回退由单元测试注入验证。文件方式保留原有较高的共享目录读写开销。操作见 [手册 29.6 节](GUI_USER_MANUAL.zh-CN.md#port-trace-timeout)。

Tcl 通信使用其自带接口，无新增 Python 第三方依赖。接口依据为 Tcl 8.5 官方 [socket](https://www.tcl-lang.org/man/tcl8.5/TclCmd/socket.htm) 和 [fconfigure](https://www.tcl-lang.org/man/tcl8.5/TclCmd/fconfigure.htm) 文档；兼容性另以 VM 的 Tcl/Tk 8.5.13 实际执行确认。

## 环境与统计口径

- VM：CentOS 7.9、Python 3.6.8、Tcl/Tk 8.5.13、Verdi O-2018.09-SP2，普通用户 `host`，代码和输出均在共享目录。Windows 单元测试为 Python 3.11。
- 峰值为监控器采到的“提取控制进程 + Verdi 进程树”合计 RSS，不含 GUI 和 Verdi 结束后的图处理，也不等同于唯一物理页或调度器记账。关闭内存监测的故障用例不使用报告中的 0 作为真实 RSS。
- 耗时是单次完整提取实测，含导入、追踪、拓扑、索引和结果写出，不是多次采样的统计均值。缓存命中、热文件缓存及设备 I/O 会影响结果。
- 真实内存压力阈值设为 0.5 GiB，实际分配并采样 RSS；没有在约 16 GiB VM 上申请 60 GiB。
- 阻塞仅在独立测试工作副本注入同步 sleep 和未提交损坏尾部。生产的进程终止、检查点回退、恢复及其余 NPI 查询实际运行。这验证处置机制，不等同于复现现场 NPI 内部死锁。

## 深层展开的边界

首轮 256 层设计在 `compiler.log` 中实际出现 `Over Maximum Hierarchy layers(50). Skip elaboration!`，Verdi 将其计作一个 warning、零 error。`vcs -kdb=only` 也生成了截断的 KDB，不能把“数据库目录存在”当成完整展开证明。48 层 wrapper 例中，最深父模块句柄可查到，但 `npiDefName` 为空且没有同一警告；工具现在明确报出缺少定义。

三项异常检测通过，表示**正确拒绝不完整输入**，不表示成功恢复 256 层时钟树。40 层正例则完成全部连接。此次没有猜测或自动修改站点 Verdi 展开参数；超过当前编译器展开能力时，需要提供由现场流程完整生成的数据库或由现场修正编译设置。

KDB 被单独搬走、旁置编译日志缺失时，工具无法从不存在的日志判断历史截断；仍执行所配置范围/模块/端口的校验。未配置的区域缺失不可能单凭目标输入推断。此边界适用于任何目标结构提取，不能以界面显示一张图代替数据库完整性检查。

探索记录均保留：`scales/deep/`、`deep-final/`、`deep-final02/`、`deep-final03/`、`deep-probes/`。其中一次测试脚本错误地要求 Verdi 的 OS 退出码非零；实测 batch 错误也可能返回 0，已改为核对失败阶段、提交状态和结果完整性。另一次尝试完整 VCS 编译在共享目录的动态库符号链接步骤失败，不计为 KDB/提取通过；正式负例采用独立的 `-kdb=only` 流程。

## 复现

使用新的输出目录，避免把不同源码版本的未完成测试混在一起。需要目标设备已有 EDA/许可环境；GUI 检查需要图形显示或 Xvfb。

```bash
source scripts/eda_env.sh
python3 scripts/check_resilience.py --out validation/my-resilience
python3 scripts/check_resilience_scale.py --out validation/my-resilience-scale
python3 scripts/check_deep_elaboration.py --out validation/my-deep-import
python3 scripts/check_target_soc.py --out validation/my-soc-regression
xvfb-run -n 180 -s '-screen 0 1920x1080x24' \
  python3 scripts/check_trace_timeout_gui.py \
  --out validation/my-timeout-gui --fixtures validation/my-port-timeout
```

`check_deep_elaboration.py` 的截断负例针对本次 Verdi 2018 环境；若另一版本能够完整展开 256 层，不能期待它产生同样的错误。`check_target_soc.py` 需要本机已有的三份开源 KDB 和既有全负载参考结果，不随便携包分发。原生超时 fixture 可用 `scripts/check_trace_timeout.py` 生成。

当前仍未拿到用户商业芯片的原始故障库，也未在现场调度器下验证真实 64 GiB 额度。本轮结果证明上述明确规模和故障机制通过，不能据此保证任意商业全芯片的 elab 导入、每个 NPI 调用或峰值内存都已验收。升级前未完成任务若实现签名不一致，需要用原版本完成恢复或用新版新建提取；不要修改签名绕过恢复检查。
